## 1. Does the score rank repositories correctly?

### Methodology

**Question.** Does the score order repositories the way an independent judgement of quality does, overall and per category?

**Why rank correlation, not accuracy.** A 0–100 code-quality score has no ground truth. Nobody can say Flask "should" score 91 rather than 84. What can be checked is whether the rubric *orders* repositories the way a reviewer would. Spearman's ρ measures exactly that. It is indifferent to the rubric's deliberately non-linear curve (`100·2^(−penalty/half-life)`), and it handles the ties a 1–5 label scale produces.

**Dataset construction.** The protocol and labels were committed *before any scan* (`ad509a9`, [PROTOCOL.md](../validation/rubric/PROTOCOL.md), [labels.csv](../validation/rubric/labels.csv)). There are 20 public repositories in the three analysed languages, each pinned to a commit SHA, in three groups:
- **vulnerable (6):** insecure by design: PyGoat, DVPWA, DVNA, DVWS, NodeGoat, Vulnerable-Flask-App.
- **mature (9):** widely deployed, actively maintained libraries and templates: Starlette, httpx, Flask, requests, DRF, Express, axios, excalidraw, the FastAPI template.
- **tutorial (5):** example and tutorial apps, some archived: the three RealWorld examples, microblog, flaskr-tdd.

pydantic was excluded because it's over the 200 MB clone limit.

**Labelling.** One labeller, the AI assistant that built CodeAudit, gave each repository a 1–5 label per category. The labels used only facts available without running CodeAudit: stated purpose, maintenance activity, archival status and general knowledge of the codebase. The protocol names the weaknesses up front:
- **One labeller, not blind to reputation.** A halo effect is expected.
- **Groups dominate.** "Vulnerable apps score low" can carry ρ on its own, so within-group ρ is the stricter test.
- **Code health is Python-only.**
- **n = 20.** The intervals are wide.

**Procedure.**
- **Scanning:** each commit was scanned through the real API with LLM enrichment off. Its findings were snapshotted to [`findings.jsonl`](../validation/rubric/results/20260918-v1.0/findings.jsonl), which holds analyzer, rule, severity, path and corroboration only, with no code.
- **Analysis:** [`report.py`](../validation/rubric/report.py) rescores the snapshot and **aborts unless it reproduces the API's stored scores exactly**. It then reports ρ with 5,000-resample bootstrap CIs, one-sided permutation p-values, within-group ρ, every inversion and parameter sensitivity.

**Deviation from the protocol.** The protocol said "scan by URL". The first attempt failed immediately because GitHub's unauthenticated API limit (60 requests per hour) was already exhausted on this machine's shared egress IP. The remaining scans were uploaded as zips of the same commits, fetched with the authenticated `gh` CLI. Two repositories (requests and the FastAPI template) contain symlinks, which zip upload rejects, so they were scanned by URL after the limit reset. The analyzers are the same either way.

### First pass: the honest, mediocre result

Rubric v1.0 as shipped ([full report](../validation/rubric/results/20260918-v1.0/report.md)):

| Dimension | n | Spearman ρ | 95% CI | p (one-sided) |
|---|---|---|---|---|
| **overall** | 20 | **0.66** | 0.30 – 0.86 | 0.001 |
| security | 20 | 0.32 | −0.22 – 0.70 | 0.08 |
| dependencies | 20 | 0.43 | −0.04 – 0.81 | 0.03 |
| architecture | 20 | **−0.16** | −0.63 – 0.29 | 0.75 |
| code health (Python only) | 13 | 0.34 | −0.34 – 0.79 | 0.12 |

Median overall score per group: vulnerable **40.5**, tutorial **69.5**, mature **74.1**. The ordering is right, but the tutorial and mature groups barely separate.

**Within groups** the rubric has almost no skill. Overall ρ is −0.32 among tutorials and 0.41 among mature repos. Security ρ is −0.71 among tutorials and −0.52 among mature repos. The overall 0.66 is mostly the vulnerable-vs-rest contrast. On this evidence, the score is useful for telling a training-grade insecure app from maintained software. It is **not** yet useful for ranking two maintained projects against each other.

141 inversions (pairs whose labels differ by ≥ 2 but whose scores disagree) break down as: architecture 46, security 36, dependencies 27, overall 22, code health 10.

### The inversions, diagnosed

Each diagnosis was checked against the findings behind the scores.

**1. "No lockfile" scored as a perfect 100 (dependencies).**
- **The inversion:** DVNA (label 1) scored 100, above Starlette, Flask and axios (label 5).
- **Cause:** DVNA, Express and DRF commit only `package.json` or `pyproject.toml`. OSV-Scanner runs with `--no-resolve`, so version ranges aren't checked at all. Zero findings meant "nothing assessed", but the rubric read it as "clean". ([`lockfiles.json`](../validation/rubric/results/20260918-v1.0/lockfiles.json) records which commits pin anything. requests does pin two dev/docs packages, so its 100 is a real, if narrow, assessment.)

**2. Dependency scores saturate at 0.**
- **The symptom:** of the 16 repositories whose lockfiles or pinned requirements produced findings, 15 scored between 0 and 42.3 (Starlette, at 75.8, is the exception). Eight scored below 1, from excalidraw (label 5) to NodeGoat (label 1), which discards ranking information.
- **Cause:** each advisory is its own rule, so repeat damping rarely applies (only when one advisory appears in several lockfiles), and dependencies aren't size-normalised. excalidraw's three `yarn.lock` files give 394 scored advisory findings (471 before dedup), for a penalty of 1,159. PyGoat's pinned requirements give a penalty of 574. The half-life of 25 is exhausted after a handful of advisories.

**3. Examples and docs counted as production code (security).**
- **The inversion:** Express (label 5) scored 38.1 on security, below four of the five tutorial apps (label 3–4).
- **Cause:** all 41 of its security findings are in `examples/`, which are sample apps that demonstrate sessions and cookies. requests' 7 template warnings are in its docs theme. The rubric down-weights `tests/` by ×0.2 but not `examples/` or `docs/`.

**4. Cycles counted per enumerated cycle, not per tangle (architecture).**
- **The inversion:** Flask (label 5) scored 48.8 on architecture, below Vulnerable-Flask-App (label 1, 98.3). microblog (label 4) scored 52.4.
- **Cause:** `simple_cycles` enumerates every elementary cycle in a strongly connected component. Flask has one 14-module component, which produced 98 reported cycles. microblog's 17-module component (the Flask-blueprint `from app import routes` idiom) produced 34, and excalidraw hit the 100-cycle cap. The same structural problem is counted dozens of times.

**5. Small apps can't have architecture problems (architecture; not fixable by weighting).**
- **The symptom:** vulnerable apps have a median architecture score of **96.4**, the highest of the three groups.
- **Cause:** a 4-module app has no room for a cycle, a layer violation or a god module. The architecture category measures *structural defects present*, not *structure quality*, so "no structure" scores as "clean structure". This is a construct-validity problem. The architecture labels were also the least grounded, as pre-registered.

**6. Detector misses and severity downgrades (security; not a rubric problem).**
- **DVPWA:** a SQL-injection training app, scored 83.0 on security. Its injectable `INSERT … VALUES ('%(name)s')" % {...}` in `sqli/dao/student.py` was found only by Bandit B608, and Bandit's *low confidence* dropped it to **info** (weight 0.5). Semgrep's registry rules didn't flag the aiopg cursor at all.
- **The Node RealWorld app:** scored 100 on security. No Semgrep rule fired on its TypeScript.
- **microblog:** scored 20.5. MD5 for Gravatar URLs, `os.system` in its translation CLI and `href` template variables are real rule hits with little real risk.

The rubric can only weigh what the analyzers report.

### What changed: four candidate fixes, tested offline

Each diagnosis above suggested a change. Each change was tested by rescoring the *same snapshot against the same labels*, without changing the shipped rubric:

| Experiment (fixes diagnosis) | security | dependencies | architecture | code health | **overall** |
|---|---|---|---|---|---|
| **v1.0 as shipped** | 0.32 | 0.43 | −0.16 | 0.34 | **0.66** |
| E1 no pinned deps → dependencies "not assessed" (#1) | 0.32 | 0.49 (n=17) | −0.16 | 0.34 | 0.61 |
| E2 advisories grouped per package, so damping applies (#2) | 0.32 | **0.39** | −0.16 | 0.34 | 0.66 |
| E3 `examples/`, `docs/`, `demo/`, `samples/` weighted like tests (#3) | **0.39** | 0.45 | −0.16 | 0.34 | **0.74** |
| E4 one cycle finding per strongly connected component (#4) | 0.32 | 0.43 | **−0.02** | 0.34 | **0.72** |
| **E1–E4 combined** | 0.39 | 0.45 (n=17) | −0.02 | 0.34 | **0.78** |

Combined, with 95% CIs:

| Category | ρ | 95% CI |
|---|---|---|
| overall | 0.78 | 0.50 – 0.91 |
| security | 0.39 | −0.12 – 0.74 |
| dependencies | 0.45 | −0.08 – 0.85 |
| architecture | −0.02 | −0.49 – 0.41 |

Inversions fall from 141 to 115.

What to take from this:
- **E3 and E4 help, and they are principled.** Sample apps aren't the product, and one tangle is one problem.
- **E1 is right on its own terms but lowers overall ρ.** It raises dependency ρ to 0.49, but removing the perfect 100 from DVNA (bad) also removes it from Express and DRF (good), and those two mattered more here. It's still the honest behaviour: an unassessed category shouldn't count as clean.
- **E2 made dependencies *worse* (0.39).** Grouping by package helps the big mature lockfiles (httpx 34.9 → 52.2, Flask 24.3 → 38.3). But it lifts the label-1 apps more: many CVEs in a few ancient packages now count as a few problems (DVPWA 0.5 → 15.9, Django RealWorld 7.1 → 28.2). This is a negative result, and E2 is not recommended as specified.
- **Architecture stays at zero.** Diagnosis #5 is untouched by any weighting change.
- **Overfitting warning.** E3 and E4 were designed after seeing these 20 repositories, and they are evaluated on the same 20. The 0.78 is an optimistic, in-sample number. A held-out set is needed before shipping them; see *With more time*.

**None of E1–E4 is shipped.** Shipped scores are still v1.0.

### Weight sensitivity

Every rubric parameter was varied on its own, and ρ was recomputed on the same snapshot ([full table](../validation/rubric/results/20260918-v1.0/report.md#sensitivity-ρ-with-one-parameter-changed)).

| Change | Overall ρ (shipped 0.66) | Takeaway |
|---|---|---|
| Any category weight ×0.5 or ×1.5 | 0.58 – 0.70 | **The 40/20/20/20 weights are not what's wrong.** Equal weights give 0.60. |
| Any half-life ×0.5 or ×1.5 | 0.62 – 0.68 | Per-category ρ is *invariant* to the half-life, because the curve is monotone. It only reweights categories in the overall score. |
| Repeat-damping exponent 0 (no damping) | **0.10** (security −0.25) | **Damping is the most load-bearing choice.** Without it, thousands of test `assert`s swamp everything. |
| Damping exponent 0.5 / 1.0 | 0.55 / 0.73 | Stronger damping helps. 1.0 (a harmonic sum) is worth testing on held-out data. |
| No size normalisation | 0.36 | Size normalisation matters. |
| Flat severity weights | 0.68 (security 0.13) | Severity weighting carries the security ranking, but not the overall one. |
| Test-path factor 0.05 / 1.0 | 0.70 / 0.60 | Down-weighting test code helps. |
| No corroboration bonus | 0.63 | Small effect. |

The ranking is robust to the weight choices and fragile to the *counting* choices: what counts as one finding (damping, cycles, advisories) and what counts as production code. That's where the diagnoses point too.

## 2. LLM fix suggestions: patch validation

**Setup.** [`validation/llm/`](../validation/llm/README.md) ran 9 of the rubric study's pinned commits (the vulnerable and tutorial apps, which have the most to fix) through the full pipeline, with enrichment on. The model was **qwen2.5-coder:7b** (Q4_K_M, digest `dae161e27b0e`) through Ollama, the free local option. **⚠ No Claude run exists.** `.env` has no Anthropic key, so the production model's pass rate has not been measured. Every LLM number in this report describes a 7B local model.

**Definition.** A suggestion counts as *valid* when its unified diff:
- touches only existing files inside the repository
- passes `git apply --check --recount` on a clean copy
- still parses after applying: `ast.parse` for Python, no tree-sitter error nodes for JS/TS

The pass rate is **valid ÷ suggestions whose patch was validated**. It excludes suggestions with no patch, and those never validated because the request failed.

| | Count |
|---|---|
| Fix suggestions generated | 171 |
| … with a patch that was validated | 145 |
| **Valid (applies and parses)** | **21 → pass rate 14.5%** |
| Failed to apply | 124 |
| No patch proposed / request failed before validation | 14 / 12 |

Why patches failed:

| Reason | Count |
|---|---|
| Not a unified diff at all (prose or a code block instead of `---`/`+++` hunks) | 65 |
| Hunk context doesn't match the file | 42 |
| Corrupt patch (malformed hunk headers) | 13 |
| Touches a file it may not (new or outside the repository) | 4 |

By the kind of finding being fixed:

| Finding from | Valid / validated |
|---|---|
| Dependency advisory (a version bump in a manifest) | **17 / 38 (45%)** |
| Ruff (lint) | 2 / 17 |
| Bandit | 1 / 27 |
| Semgrep | **1 / 63 (2%)** |

**Reading it.**
- The 7B model can edit a version pin. It almost never produces an applicable diff for a code-level security fix.
- The validator is doing its job: all 124 broken patches were recorded as not valid. By design they can't be offered as fixes or included in a PR: the API returns `patch` only when `valid`, and the PR builder only uses verified patches.
- An earlier uncontrolled pool (94 suggestions from ad-hoc scans of other projects on 2026-09-17/18, same model) passed at 26.7% (23/86): [counts](../validation/llm/results/20260917-adhoc-qwen2.5-coder-7b/report.md). ⚠ It can only be regenerated against the database those scans live in. It had a higher share of dependency fixes.
- **Not yet measured:** whether valid patches are *correct*. "Valid" doesn't mean "fixes the vulnerability" or "passes tests".

Fix-request latency on a laptop: p50 11 s, p95 32 s. 18 of 131 LLM calls failed. In 17, the output was unusable after one correction attempt: 9 were missing a required field and 8 were invalid JSON. One hit the 4,096-token output limit.

## 3. Architecture review: citation hallucination rate

**Setup.** Same 9 scans and model. The review sees a digest of the import graph, never the code. Every piece of evidence it cites is checked against the scan's `graph_nodes` and `graph_edges`: a module, a directory, or an import `a -> b` that must exist.

| | Result |
|---|---|
| Reviews completed | **6 of 9**. The other 3 failed, all on invalid JSON (after one correction attempt). |
| Module references cited (stored `hallucination_rate` denominator) | 56 |
| Invalid module references | **0 → hallucination rate 0.0%** (95% upper bound ≈ 5%, rule of three) |
| Evidence citations rejected by the verifier, any reason (stricter) | **0 of 38** |
| Fabricated import edges between real modules | 0 |
| Issues kept / dropped for lack of valid evidence | 9 / 0 |

**Why 0% is less impressive than it looks.**
- **Restated paths:** every kept citation is a real module path, and most "issues" restate cycles and orphans the analyzer had already reported (for example, microblog's `app/api/__init__.py -> app/api/errors.py`). The citations are listed per review in [`metrics.json`](../validation/llm/results/20260918-qwen2.5-coder-7b/metrics.json) (`kept_issues`).
- **Easy to satisfy:** the verifier accepts any real directory as evidence, which is a low bar.
- **Measured faithfulness, not insight:** a small model that repeats its input doesn't hallucinate paths, but it adds little. Measuring review *usefulness* needs human rating, and that hasn't been done.

**A gap in the metric itself.** The stored `hallucination_rate` counts only references to modules that don't exist. A cited import `a -> b` between two *real* modules that doesn't exist is rejected and removed, but **not counted** (`verify_evidence` returns 0 invalid references for it). The stricter rejected-evidence rate above counts it. It happened 0 times in this run, so the two rates agree here, but the stored rate can understate fabrication in general. This should be fixed in `architect.py`.

An earlier uncontrolled pool (5 reviews, 2026-09-17, [counts](../validation/llm/results/20260917-adhoc-qwen2.5-coder-7b/report.md)) also had 0 invalid out of 52 module references, and 1 of its 5 reviews failed.

## 4. Phishing / clone risk detection

### Methodology

- **Data:** [`validation/phishing/`](../validation/phishing/README.md). Positives are 150 URLs from the OpenPhish feed (52 of them were already dead when checked). Negatives are 138 legitimate pages: 38 official login and home pages of impersonated brands, plus 100 sites sampled from the Tranco top list.
- **Capture:** every URL was loaded in the same sandboxed capture the product uses. Only pages that actually rendered (`ok`) are scored.
- **Dead URLs:** 35% of the phishing URLs (52 of 150) were dead or taken down by the time they were checked, the same day they were fetched from the feed. Those are reported, not silently dropped.
- **Label leakage:** positives come from OpenPhish, which is also one of the score's reputation signals. **Headline metrics exclude reputation signals.** The full score (AUC 1.000) is shown only to make the leakage visible.
- **Why ROC AUC plus fixed thresholds:** the score is an explained sum of evidence points, not a calibrated probability. AUC measures separation. Precision and recall are reported at the three thresholds the UI actually uses (*moderate* ≥ 20, *high* ≥ 45, *very high* ≥ 70).

### First pass (model v0.1, 189 scored URLs)

The first run gave ROC AUC 0.901. At the *moderate* threshold, precision was 0.923 and recall 0.367. Best F1 was 0.892, at score ≥ 1.

### The false positives and misses, diagnosed

| Case | Diagnosis | Change in v0.1.1 |
|---|---|---|
| **gov.uk (HMRC's own page) scored 60**: "100% visual similarity to HMRC" (+35) and "favicon identical to HMRC's" (+30) | The visual matcher compared the brand's *official* site with its own reference screenshot | Visual and favicon matches are suppressed when the page is on the brand's official domain |
| Phishing on `*.weebly.com`, `*.godaddysites.com`, `*.gitbook.io`, `*.railway.app` and `quickconnect.to` scored **0**, because `domain_age_over_3y` (−8) credited the *platform's* age | A free-hosting subdomain inherits the platform's registration date and trust | Those platforms were added to `hosting_platform` (+6), and platform subdomains no longer get the domain-age trust bonus or the platform's TLD/MX signals |

Diff of fired signals between the runs, per URL ([`diff_runs.py`](../validation/phishing/diff_runs.py) on the raw results): `domain_age_over_3y` stopped firing on 7 platform-hosted phishing pages and `hosting_platform` started on 5. The gov.uk visual and favicon matches were removed. One certificate signal changed on a legitimate site (arin.net) because the page was captured again, which is noise from re-fetching live sites.

### Final results (model v0.1.1, 188 scored URLs: 98 phishing, 90 legitimate)

The run re-evaluated the 189 URLs that were live in the first pass. One more legitimate page failed (a memory limit), leaving 188.

| Threshold (without reputation) | Precision | Recall | F1 | False-positive rate |
|---|---|---|---|---|
| **≥ 20 (moderate, the UI's warning level)** | **0.949** | **0.378** | **0.540** | 0.022 |
| ≥ 45 (high) | 1.000 | 0.082 | 0.151 | 0.000 |
| ≥ 70 (very high) | n/a | 0.000 | 0.000 | 0.000 |
| ≥ 1 (any signal; best F1) | 0.909 | 0.918 | 0.914 | 0.100 |

ROC AUC: **0.927** without reputation, and 1.000 with it (leaked).

**Read this honestly.**
- **Moderate threshold:** without reputation feeds, the heuristics flag about 38% of live phishing at 95% precision.
- **Best F1:** the 0.914 is at a threshold of 1 ("any risk signal fired"). That's a statement about separation, not an operating point anyone should alert on.
- **High and very high levels:** almost no unlisted phishing reaches them. In practice, those levels are reached through reputation feeds.

The remaining misses are mostly pages on free hosting (`*.vercel.app`) that copy no brand name into the title or domain, and pages on long-registered compromised sites.

### Per-signal contribution

From [the v0.1.1 report](../validation/phishing/results/20260917-v0.1.1/report.md). The columns are:
- **AUC drop:** how much the headline AUC falls when that signal's points are removed.
- **Coef.:** the coefficient of a regularised logistic regression fitted to these labels.

| Signal | Points | Fires on phishing / legit | AUC drop | Coef. | Verdict |
|---|---|---|---|---|---|
| hosting_platform | +6 | 51% / 0% | **0.116** | 1.19 | the most predictive signal, yet weighted only +6 |
| domain_age_over_3y | −8 | 10% / 82% | 0.055 | −1.14 | strong trust signal |
| no_mx_record | +3 | 34% / 14% | 0.025 | 0.58 | predictive, low weight |
| tld_elevated_risk | +4 | 7% / 4% | 0.006 | 0.22 | weak |
| brand_in_title | +15 | 24% / 0% | 0.003 | 0.49 | discriminative but redundant |
| brand_in_domain | +20 | 11% / 0% | 0.002 | 0.19 | redundant |
| password_field | +8 | 28% / 18% | **−0.009** | 0.22 | slightly *hurts* AUC: legitimate login pages ask for passwords too |
| cross_domain_redirect | +4 | 10% / 8% | −0.002 | 0.15 | weak |
| cert_untrusted, cert_hostname_mismatch | +12, +15 | 2% / 1% | −0.002 | −0.05 | noise at this sample size |
| favicon_match, visual_match_strong, credential/payment forms | +10 to +35 | ≤ 1% | ≤ 0.006 | — | too rare to judge with 98 positives |
| reputation_openphish_url | +60 | 100% / 0% | — | 4.57 | leaks labels (excluded) |

The weights are hand-set priors (model `0.1.1-prior`), and the data says they are **mis-ordered**:
- the most predictive signal (`hosting_platform`) is among the lightest
- the heavy visual and form signals almost never fire on real phishing

Refitting the weights needs a larger dataset with a proper train/test split. It hasn't been done.

**Why it dropped.** This commit added the validation, load-test and demo scripts. The findings snapshot is [`self-scan-findings.jsonl`](self-scan-findings.jsonl), and `scripts/selfscan_breakdown.py` recomputes these figures from it. That is diagnosis #3 again: developer tooling is scored as production code.

The dependencies score of 100 is a real assessment. CodeAudit commits `uv.lock` and `package-lock.json`, and OSV-Scanner found no advisories in either.

## What I would do with more time

1. **A held-out rubric set with more than one labeller.** 40+ repositories, labelled blind to project names by two or three people from a written rubric, with inter-rater agreement (Krippendorff's α). E1, E3, E4 and damping exponent 1.0 should be tested there before any of them ships as v1.1.
2. **Replace the architecture category's construct.** Measure structure quality, not only defects: modularity (Newman Q) of the import graph, the share of modules in cycles rather than the cycle count, and depth versus breadth. Diagnosis #5 can't be fixed by weighting.
3. **Stop severity downgrades from hiding confirmed injections.** Bandit's low-confidence step-down turned DVPWA's real SQL injection into an info finding. Evaluate detector recall directly on the vulnerable apps' known vulnerability lists (OWASP Benchmark-style), separately from the rubric.
4. **Measure the fix suggester with the production model.** Every LLM number here is from a local 7B model. Run the same `validation/llm` set with Claude, and add tests that *execute*: "valid" today means "applies and parses", not "compiles and passes tests".
5. **Refit the phishing weights** on a larger, time-split dataset: train on week 1, test on week 2, with negatives from the long tail rather than the Tranco top list.
6. **Count the stricter hallucination rate in the product.** The stored rate ignores fabricated import edges between real modules; see §3.
